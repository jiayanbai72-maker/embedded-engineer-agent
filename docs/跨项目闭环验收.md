# 跨项目闭环验收

目标是确认已有通用模块通过真实 HTTP 服务连接起来，不接真实模型，不要求开发板，不修改用户项目。

运行 `tools/verify_agent_closed_loop.py`（PYTHONPATH 指向项目 src），默认输出到 runtime/acceptance。三个场景在系统临时目录和随机本地端口运行；每例独立工程、控制器、任务计划和交付包，结束后清理临时数据。测试决策者只通过 Python 构造 make_server 的显式参数注入，没有新增浏览器端注入接口，也不受生产模型环境变量影响。

| 场景 | 被验证的行为 | 显式故障 |
|---|---|---|
| 环境监测 | 30度边界、正常读数、非有限值拒绝 | 大于阈值写成严格大于，边界测试失败 |
| 执行器控制 | 小于下限、中间值、超过上限的限幅 | 缺少冒号，真实编译失败 |
| 记录设备 | 空缓存、容量内、超过容量保留最近三条 | 无；不验证真实低功耗 |

共同路径：创建项目→自动提问→自然语言回答→分析草稿→测试用户确认需求→测试用户选择方案→检索缺资料并记录失败→任务规划→实际源码编译→实际单元测试→生成ZIP→完成任务计划。前两例在失败点关闭并重建HTTP服务，恢复失败状态后重新规划与修复，确保没有因重启重复提交实现。

下载两次核对内容一致；检查需求、已选方案、源码、测试结果、交付完整性报告齐全且硬件未验证。最后补充需求，确认旧产物失效并拒绝下载旧交付。

固定夹具根据实际状态选择预先编写的分析和修复。此验收证明控制、依赖、权限、恢复、构建、测试与交付机制连通，不证明语言模型能理解任意需求、自主写代码、定位故障、做器件选型或完成真实硬件工程。用户确认通过HTTP测试请求模拟，没有把它计为模型权限，也没有验证浏览器视觉布局。

运行结果包括报告.md、report.json（含逐步时间线）、三个场景的交付ZIP。临时项目ID仅供追踪，临时目录清理后不再是工作台中的可打开项目。

后续重点：真实模型联调及能力评估、用户界面端到端检查、复杂设计/功耗契约细化。板卡适配与实机验收仍单独开展。
