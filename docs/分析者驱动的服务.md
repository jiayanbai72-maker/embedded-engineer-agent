# 分析者驱动的本地服务

本版由本次对话中的 Codex 承担分析与判断，服务负责检索、契约检查、状态、确认、执行和交付。
它不是服务内部已经拥有独立推理模型，也不是随机返回固定模拟结果。
没有分析者提交结果时，项目保持 awaiting_analysis。未来真实模型可以接管同一分析契约。

## 判断与执行

分析输入为项目描述、用户补充、通用知识和工具能力。分析结果包括功能、约束、验收、未知项、方案取舍、判断依据和动作。
当前支持文档 ZIP 和主机行为原型执行；MCU 编译、烧录、硬件验证没有接入，始终标为未执行。
更新：增加 host_prototype 动作与主机行为原型适配器。提交 Python 源码后，执行真实 py_compile 和 unittest；它不代表 MCU 固件构建。
新增 POST 操作 implementation（revision、files、rationale）、build（revision）、test（revision）。测试失败可以提交最小修复，必须重新编译再测试。
该执行器会运行分析者提交的代码，因此仅在可信本地演练使用；它有超时但不是安全沙箱，不适用于不受信任用户或公共部署。
我提供的门窗示例是针对该描述写出的判断记录：先区分附近和远程查看，不在缺少续航与网络约束时指定芯片。
服务只检索与引用检查，不负责验证自由文本结论是否正确；分析来源保留在项目档案中。

## 启动

设置 PYTHONPATH 为 src 后，在项目根目录运行：

```text
python -m embedded_agent.server --port 8765
```

仅绑定 127.0.0.1，单进程，无模型 API。已提供同源工作台页面，不提供远程认证或公共部署能力。
新服务使用原来的 runtime/projects，因此重启后可以恢复状态。

## HTTP 接口

| 方法 | 路径 | 内容 |
|---|---|---|
| GET | /health | 服务健康与分析模式 |
| POST | /projects | description，创建项目并等待分析 |
| GET | /projects/{id} | 状态、产物与事件 |
| POST | /projects/{id}/analysis | revision、analyst、requirements、comparison、decision |
| POST | /projects/{id}/supplement | revision、message，清除下游结果并等待重分析 |
| POST | /projects/{id}/confirm | revision、confirmed=true，确认需求 |
| POST | /projects/{id}/select | revision、candidate_id，选择方案 |
| POST | /projects/{id}/execute | revision，执行已批准的文档交付动作 |
| GET | /projects/{id}/download | 下载已执行生成的文档 ZIP |

POST 需要 application/json。每次更新需要提交当前 revision，避免对过期草稿确认。
阻塞问题存在时拒绝确认，必须补充并重分析。确认需求不等于器件与实机验证通过。
用户选择后状态为 ready_delivery，实际 ZIP 生成成功后才变成 documents_delivered。
文档包可以重新生成并校验哈希；新增需求使旧交付失效，但历史记录保留。

示例分析契约见 examples/analyst-door-monitor.json，仅供独立测试；其中的确认和方案选择不能代替真实用户确认。

## 验收

测试实际启动 HTTP 服务，创建项目、提交分析、确认、停服重启、继续选择、执行并下载 ZIP。
同时验证顺序、版本、阻塞问题、修改后失效和未执行状态。
这是服务流程验收，不是模型分析效果或固件交付验收。
