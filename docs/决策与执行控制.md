# 决策与执行控制模块

本模块将下一步决策与工具执行分离：读取任务上下文 → 提交决策 → 校验 → 执行 → 持久化观察 → 再次决策。
当前决策提供方是外部分析者；没有接入真实模型时默认等待决策，不使用固定流程冒充智能推理。

## 已实现

- 统一上下文包含项目需求、约束、方案、证据、源码、执行日志、历史观察、可用动作和剩余预算。
- DecisionProvider 可由分析者适配器或后续模型实现；tick 每次至多执行一个动作，便于检查和反馈。
- 决策包含唯一 id、project_revision、action、arguments、rationale、expected、source。
- expected 记录预期，不作为实际成功证据；下一轮依据 tool_result 与 project_status 判断。
- 白名单动作：analysis、implementation、build、test、execute、ask、finish。
- confirm/select 保留为用户操作，决策提供方不能擅自确认。
- ask 保存具体问题并停止；用户通过项目补充接口回复后，refresh 获取新上下文。
- finish 只允许已生成交付包的项目；完成范围仍是主机原型与文档，不是实机项目。
- 默认最多20个动作、3次失败后的代码修复；可在运行创建时缩小或调整预算。
- 同一决策id和内容重复提交返回既有结果，内容变化则拒绝。
- 项目变化后拒绝旧上下文；待执行旧动作发现变化时记录 stale，不执行。
- 工具执行前保存 executing；重启后发现服务提交事件则恢复观察，不重复执行。
- 无法确定动作是否已发生时保持 interrupted_unknown，禁止自动重试不确定副作用。

## HTTP 入口

| 方法 | 路径 | 参数 |
|---|---|---|
| POST | /runs | project_id、max_steps可选、max_repairs可选 |
| GET | /runs/{id} | 返回完整上下文 |
| POST | /runs/{id}/decisions | revision、decision |
| POST | /runs/{id}/tick | 空对象即可；执行待处理决策 |
| POST | /runs/{id}/refresh | revision；用户操作后同步新上下文 |

```json
{
  "revision": 0,
  "decision": {
    "id": "DEC-001",
    "project_revision": 4,
    "action": "build",
    "arguments": {},
    "rationale": "源码已提交，先构建再决定是否运行测试",
    "expected": "获得真实编译结果，失败则根据日志修复",
    "source": "本次对话中的分析者"
  }
}
```

run revision 与 project revision 是不同版本号，调用前应读取 GET /runs/{id}。
项目状态与运行状态分别保存，运行记录位于 runtime/control-runs。
新模型实现只提供结构化决策，不直接执行任意命令，也不提供用户确认权限。

## 当前边界

单进程本地服务，不承诺多进程并发事务；待部署时应换事务数据库和作业队列。
源码测试执行器只用于可信本地项目，有超时但不是安全沙箱。
控制器验证动作与前置条件，不验证自由文本判断是否正确；分析效果需在接入模型后另行评测。
当前没有自动联网、自动烧录或修改不可逆设备配置能力。
中断状态 interrupted_unknown 需人工核查执行记录后创建新运行；不提供一键强制重试。

## 验证

测试覆盖真实主机故障与修复、成功交付、等待信息、拒绝越权与提前完成、重复请求、旧上下文、预算、重启恢复和决策提供方接口。
测试中的决策提供方是明确的契约替身，不是独立推理模型。
