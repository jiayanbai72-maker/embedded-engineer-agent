# 缓存命中排查与优化

更新：2026-10-18。本轮不调用付费模型，不为预热缓存发送额外请求。

## 发现

本地账本中，2026-10-17 有 API 缓存用量记录的 94 次调用：命中输入 597120 token、未命中输入 1411208 token，加权命中率约29.73%。更早未记录缓存分类的调用不在这一统计中，不能当作零命中。2026-10-18 检查时尚无实际模型调用，不能声称新版本已有线上命中率提升。

1. 原请求将整个动态上下文排序后放进最后一条消息。定向修复中，feedback 按字母顺序排在 files 之前，新报错会使后续相同源码也无法共享完整前缀。
2. 文件按名字排序时，常改的生产 `.c` 文件出现在头文件及原测试之前，后面的固定输入得不到前缀复用机会。
3. 完整文件哈希如果放在文件正文之前，文件尾部的小变化也会从哈希处提前截断前缀。
4. 普通决策请求已单独发送项目需求，但动态项目中又重复包含它们。定向修复还携带了无意义的空项目基线。

## 当前修正

`prompt_layout.py` 对请求做确定性、无损重排：

- 固定系统说明与契约最先发送。
- 需求基线只发送一次，不删减验收和约束。
- 定向修复先发送冻结扩展用例、原测试，再发送头文件及生产源码。
- 每个文件单独成消息，保持稳定顺序；当前哈希放在对应正文之后。
- 报错、验证结果、修复反馈等变化频繁的数据放在最后。
- 不修改项目存储，不复用过期源码，不把旧哈希当成当前哈希，不删测试。
- 工作台已有的确定性复测、打包与结束调度继续避免不必要的模型请求。

该布局用于 BudgetModel 的所有调用；定向修复分段同时适用于工作台和独立脚本。不同角色的系统任务说明不同，不能假定跨角色请求具有同样的缓存前缀。

## 离线测量

使用当前机器人源码与八类冻结边界用例，只在内存中构造对比，没有发送给模型、没有改动工程代码。

| 场景 | 原布局相同前缀 | 新布局相同前缀 |
|---|---:|---:|
| 只改变错误反馈 | 8900 UTF-8 字节 | 27582 UTF-8 字节 |
| 在生产文件末尾变化 | 18022 UTF-8 字节 | 26076 UTF-8 字节 |

这些是序列化请求的本地字节数，不是模型 token，也不是命中率预测。不使用这些结果修改费用账本或显示虚构的缓存收益。可复跑 `tools/audit_prompt_cache.py --project PROJECT_ID`；结果保存在 `runtime/cache-audit/latest.json`。

## 后续如何判断

DeepSeek 官方说明缓存自动启用，命中需要匹配已持久化的前缀。最终仍以真实请求返回的 `prompt_cache_hit_tokens` 与 `prompt_cache_miss_tokens` 为准。[官方缓存说明](https://api-docs.deepseek.com/guides/kv_cache/)

首次请求、新角色说明、测试集变更、早部源码变化、供应商缓存未持久化等情况下，命中可能降低。布局优化不承诺固定命中率；不填充无意义内容、不发送重复预热请求，也不增加调用次数来制造漂亮的百分比。

节省费用以总输入、未命中输入、输出及总花费共同判断。下一次有正常工程任务时再观察真实用量，无需为检查缓存专门花钱。
