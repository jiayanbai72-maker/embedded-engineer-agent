# 图纸与代码草案流程

已接受待验证项的初步方案可通过用户操作 start_draft 继续，原研究包与记录不删除。此操作不调用模型、不自动开始付费运行。模型不能代替用户执行该确认。

模型可用 draft_artifacts 顺序提交三个阶段：

1. interfaces：Markdown接口与引脚表；未核实引脚明确写TBD。
2. circuit：connections.json连接清单，每条含from、to、signal、status（proposed或unverified）。程序据清单生成惰性SVG连接草图；不接收可执行SVG，不宣称PCB生产图。
3. firmware：实际.c/.h及说明。未核实硬件由显式适配接口隔离，不能宣称可烧录固件。

每阶段需要依据、假设、未解决项。上游文件改变会清除下游草案，旧草案进入事件历史。三阶段齐全后才允许打包草案；初步研究资料包仍可单独导出，不代表完成工程。文件进入engineering-draft/目录，带清单和哈希。

当前检查仅为文件结构、路径、连接清单和阶段依赖校验。编译、电气规则和硬件验证均未执行，保持not_run。它是可继续开发的工程草案通路，而非自动完成硬件认证的工具。

缓存：固定契约前缀不含当前观察编号或动作列表；后部保留动态允许动作与真实编号目录。cache_usage保存升级后每次用量中的缓存命中/未命中token，旧记录无法追溯，不会伪造命中率。供应商缓存命中不保证。每日费用保护保持不变。


## 智能体自验证闭环

固件阶段保存一个test_*.c主机测试入口和断言后，智能体调用draft_verify（cpu须明确选择）。工具实际执行ARMCC目标编译与MSVC主机断言测试，日志和源文件哈希保存在draft_verification及runtime/draft-checks。通过状态是draft_verified，才可打包；固件链接和硬件始终另计。

失败时模型用draft_edit逐文件提交修复（当前文件SHA256、完整新内容、依据），不能改测试文件。修改使旧验证失效，必须重测。失败测试不能通过删文件、改弱断言或NDEBUG跳过。修复机会计入运行max_repairs，耗尽或本地工具不支持时停止后续模型调用。重复同源码验证由重复工作保护拦住。

本地主机C执行不等于硬件验证，也不能证明提交的测试充分覆盖全部需求。测试质量仍需审查。历史的人工修订与模型自行修订通过来源字段和事件记录区分。


## 失败变量诊断与停滞保护

主机断言失败时，工具可在独立副本中对纯标量比较添加读数，再重放测试。原测试内容、原源码哈希与原失败判定不变；诊断重放不用于宣称通过。函数调用、赋值、自增、指针解引用、数组访问等表达式不自动探测，诊断失败也不影响原失败结果。

报告包含file、line、expression与actual_values，工作台可展开查看，模型修复上下文直接提供这些数据。连续两次不同源码修订若仍在相同断言处得到相同变量值，运行暂停，避免继续付费尝试。用户提供新信息后可继续，但不清零费用或修复额度。
