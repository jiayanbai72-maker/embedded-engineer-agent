# 整机功耗估算与初步设计

购物网站报价暂缓，预算保持待核价。设计阶段可使用带依据的估算，未实测不再作为初步设计的统一阻塞条件，但不会变成实测通过。

## 使用

工作台选择项目 → “功耗估算” → 选择候选 → 查看典型和保守结果。展开“分析者估算输入”可修改情景 JSON，再“计算并保存估算”。两条纸盒机器人候选已存入示例估算，所有整机功率、电池和时长假设均有明确说明。

“以估算继续初步设计”是用户操作：勾选接受未解决事项并填写理由与验证安排。保守情景不足时也允许继续明确电源、接口、机构等初步设计，但不足、峰值未知和待核价仍保留。它不是采购批准、烧录许可、完整选型通过或48小时验收。该动作没有开放给模型决策控制器。

继续后状态为 preliminary_design，可生成带估算和未解决事项的初步文档包。现有项目授权仅交付文档时不会因此自动扩展为硬件或代码实现。

## 模型与公式

各工作状态互斥，时长覆盖目标窗口。最多一个状态的 duration_s 可为 remaining，表示目标总时间减去其余状态的时间。监听、识别、动作如果同时发生，其负载合并在该状态的 load_mw 内，不能把状态时间叠加。

功率边界固定为 whole_load_bus：稳压输出侧所有负载的总功率。升压/稳压转换损耗通过 conversion_efficiency 计算；电池侧静态损耗另列 battery_overhead_mw，避免重复计入。

- 可用能量 Wh = 电池电压 × 容量mAh / 1000 × 可用容量比例 × (1 − 储备比例)。
- 目标负载能量 Wh = 各状态负载mW × 时间秒 / 3,600,000 之和。
- 电池需求 Wh = 目标负载能量 / 转换效率 + 电池侧静态损耗mW / 1000 × 目标小时数。
- 预计续航小时 = 可用能量 / 本窗口电池侧平均功率W。

预计续航是按输入的平均工况外推；若每天动作次数随运行时间变化，需重算。可用容量折减与储备分别表示不同假设，分析者应说明各自含义。效率或负载随状态差异较大时，当前统一效率模型需改用更合适的边界，不应填出虚假的精度。

每个电池参数、效率、静态损耗、状态时长和状态功率均分 typical / conservative。保守功率不能更小、保守电池能量参数和效率不能更大；状态时长变化后保守总耗能也不能更低。缺失输入用 null，不能默认为0。

## 输入

完整可运行示例：examples/robot-power-low_power.json、examples/robot-power-dev_board.json。模型包含：

- analyst、scope、schedule_basis：分析来源、范围和工况解释。
- target_hours、reserve_fraction。
- battery：voltage_v、capacity_mah、usable_fraction 的两种情景及 basis。
- conversion_efficiency、battery_overhead_mw 的两种情景。
- states：name、duration_s、load_mw、source_type、basis，以及可选 sources。
- peak：load_peak_ma、supply_limit_ma、basis。必须是同一电压轨；未知用 null。

source_type 是来源声明：assumption、datasheet_estimate、measurement_estimate。measurement_estimate 也不构成测量凭证审核；当前没有测量日志认证功能。datasheet_estimate 必须包含 sources，引用 document_id、page、quote；服务核对引用确实在对应页面并保存原始文件哈希，但不自动证明这些文字足以推导整机功率。

引用模组3mA不等于整机3mA。若还估入主控、载板、开关和漏电，应把整机数值明确标为假设或推算。纸盒机器人示例采用 assumption，并保留模组原文作参考。

## 结果与继续条件

- estimated_meets：在声明情景下能量估算满足目标，待实测。
- estimated_shortfall：能量估算存在缺口。
- insufficient_data：关键估值缺失；需要补齐明确假设后才能继续。

整体按保守情景判断，不采用两者平均。峰值结果独立列出，平均续航满足也可能峰值供电不足。峰值只比较估算电流，未验证压降、瞬态、保护及堵转持续时间。hardware 始终为 not_run，budget_status 为 deferred_pending_quotes。

保存估算绑定当前候选及需求指纹；候选、需求或引用文件变化需重算。更新估算会使旧初步设计确认、交付和下游构建失效，旧记录保留在事件中。

## 接口和持久化

- POST /projects/{id}/power_estimate：{revision,candidate_id,model}。也可通过决策控制器 power_estimate 动作调用，结果写入观察记录。
- POST /projects/{id}/proceed_estimated_design：{revision,candidate_id,confirmed:true,accept_open_items:true,rationale}。仅用户操作，不作为模型动作。

估算保存于项目 artifacts.power_estimates；初步设计确认保存于 preliminary_acceptance。重启后可读取。交付包含 power-estimates.json 和 preliminary-design-scope.json，README 明确是保留未解决事项的初步文档。

## 本轮结果

两条纸盒机器人候选的场景假设得到：独立主控路线约72小时典型、22小时保守；集成主控研究备选约105小时典型、28小时保守。这些不是实测结果，也不能证明后一条更优，其整机功率和可编程性均未确认。两条路线保守情景都不足48小时，峰值未知，不能给出已满足续航的结论。

后续可以在保留这些缺口的前提下做初步设计，再通过降低常开负载、明确电池容量和动作模式收敛估算。
