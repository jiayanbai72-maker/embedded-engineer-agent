# 候选方案、证据研究与反馈调整

本层接在已确认的通用需求之后，复用资料检索、审核参数和约束计算。核心实现不依赖纸盒机器人、某种主控或固定物料表。

## 能力与边界

分析者提出至少两种不同候选，说明组件、架构、需求覆盖、取舍、风险、假设、数值检查与研究问题。服务执行真实本地检索和全部候选的约束计算，生成带编号的观察、缺失输入与证据缺口。分析者依据观察调整下一轮或给出条件式推荐。

当前没有自主模型或内置的器件设计推理器。本次由 Codex 作为外部分析者提供候选和下一步判断；后台没有用假模型自动重放并冒充推理。未来模型可替换分析者，通过已有 DecisionProvider 契约读取上下文并提交动作。持久化的是工程判断摘要、理由、工具结果和可核对引用，不要求模型公开内部思维链。

`needs_evidence` 与 `failed` 不同。未审核的假设可以用于情景计算，但即使算出超标，也只能说明该情景的风险，不能证明某个实际器件不合格。检索命中也不自动审核参数。

## 工作台

选择项目，进入“方案推演”：

- 本轮工程判断：比较范围、分析来源、推荐理由与观察引用。
- 候选方案：组件、架构、取舍、风险、假设及逐约束结果。
- 待补证据：缺失数值、未绑定参数和下一步取证方向。
- 检索任务：问题、检索词、为什么查询、原文链接与物理页码。
- 调整记录：历轮方案与变更理由。完整检查与历史保留在项目 design_loop 中。

“检索下一项资料”执行已安排的一个实际研究任务。“检查全部候选”重新计算，新的观察编号替代当前比较；之前评估保留在 evaluation_history。“确认此方案”仅对通过本轮声明约束且声明覆盖全部需求的候选开放，仍不代表实机验收；之后通过“资料与证据”中的“确认选型并继续”进入实现或文档交付范围。

分析者可复制当前上下文，在展开的提交入口填写 plan JSON，也可通过决策运行调用下述动作。项目版本变化会使原提交依据过期。

## 通用动作契约

四个动作均通过 `POST /projects/{id}/{operation}` 携带项目 revision，或通过决策运行提交并执行：

1. `design_plan {plan}`：创建首轮，或在上一轮已有检查后提交调整。
2. `design_research {task_id}`：执行指定任务的真实本地检索；返回 R 开头的观察编号。
3. `design_evaluate {}`：检查全部候选；返回 E 开头的逐检查观察、状态和缺口。
4. `design_recommend {candidate_id,rationale,observation_ids}`：给出带观察引用的建议。证据不足时状态只能 conditional，确认失败的候选不可直接推荐。

`design_accept {candidate_id,confirmed:true}` 是用户操作，不在模型可执行动作中。确认时重新读取参数记录并检查来源版本，避免用过期评估通过。启动新一轮会使旧选型、实现、构建及交付失效，旧数据保存在事件记录。

plan 字段：

```json
{
  "analyst": "实际分析来源",
  "scope": "本轮检查范围与未覆盖事项",
  "rationale": "为何分解成这些问题并比较这些候选",
  "objectives": [{
    "id": "ENERGY", "kind": "energy", "description": "连续监听目标",
    "requirement_ids": ["REQ-1"], "fixed_inputs": {"hours": 48}
  }],
  "candidates": [
    {
      "id": "OPTION-A", "name": "架构A", "architecture": "模块和数据流",
      "covers": ["REQ-1"], "components": [{"role": "主控", "model": null}],
      "tradeoffs": ["取舍"], "risks": ["风险"], "assumptions": ["明确假设"],
      "proposal": {"checks": [{"id": "ENERGY-A", "objective_id": "ENERGY", "kind": "energy", "inputs": {"hours": 48}}]}
    }
  ],
  "tasks": [{
    "id": "LOOKUP", "question": "需要验证什么？", "query": "型号及关键词",
    "why": "该信息如何影响方案", "candidate_ids": ["OPTION-A"]
  }]
}
```

这是字段示意，不是可直接提交的完整案例：实际需 2—6 个候选、每种计算类型的完整输入（未知数值用 null），并为每个候选覆盖所有声明目标。完整示例见 examples/robot-design-round1.json、robot-design-round2.json。

冻结字段包括预算上限、目标续航、资源需求数量等。后续轮次 objectives 必须与第一轮完全一致；不能通过删除检查或放宽需求制造通过。修改需求应走用户补充流程。

调整需增加 `response_to`（上一轮有效观察编号）与 `changes`（candidate_id、reason、observation_ids）。每个发生组件、架构或检查输入变化的候选均要说明原因；没有实质变化的重复提交被拒绝。引用是否在工程语义上充分支持调整仍由可信分析者负责，服务只验证真实存在、范围和版本一致性。

每轮最多12个研究任务、6个候选、每候选24个检查、每项目最多10轮；决策运行另有步骤预算。研究结果、旧评估和各轮提交重启后保留。

## 已完成的纸盒机器人验证

已在实际项目完成两轮，决策运行编号 `1985076c-06c8-4399-971f-f684cae5e19b`，共14步观察：首轮方案、4次检索、比较、2次原文读取、第二轮调整、3次检索、复查、条件式推荐。

首轮比较 SU21T＋独立低功耗主控与 SU03T＋现成开发板。对后者额外做了明确标注的风险情景：假设3.7V/2000mAh、85%可用率、20%储备、1W监听与2W动作，计算得到可用5.032Wh、需求约48.042Wh。所有情景输入均未审核，不是器件实测或最终电池方案，报告保持 needs_evidence。

实际读取 SU21T 规格书物理第6、7页后，分析者把第二个候选调整为复用模组内部主控的精简研究路线。PWM复用引脚表不证明三路PWM并发或应用固件可编程，因此通道数量继续未知，报价和整机功耗也未填造。48小时、100元、3路PWM目标原样保留。

第二轮两条路线仍待补证据。暂以独立主控路线作为取证优先级，属于条件式建议，不是采购确认。未自动选择方案、生成新固件或标记整机通过。

## 验证与后续

合成测试验证了“有审核证据的候选失败 → 引用真实观察调整组件 → 重新检查通过”，同时检查需求放宽、遗漏检查、虚构引用、证据不足、用户确认权限、持久化及交付追溯。合成参数不用于实际器件。

当前仍缺采购报价和测量凭证的正式导入审核、完整引脚/时序/峰值电流等检查器、自主模型驱动与真实硬件验证。功能覆盖 covers 是设计声明，不能替代功能实现测试。
